## 一、核心需求（第一轮）

- 接入名单落在 `~/.infocenter/config.json`，用户可编辑，或用命令维护：
  - `ic agents add <名字> [-d 描述] [--role coordinator]`

### R2. 到信自动提醒 ✅

- **agent 没开**：MCP 激活（initialize）后第一次轮询 `since=0`，把积压未读**马上**提醒一次。
- 兜底通道：部分客户端不向模型展示 logging 通知 → 所有 ic 工具的返回结果末尾附加未读提醒（`你还有 N 封未读…`）。
- 双开关：`ic mcp --no-notify` 可关闭推送（见 R4 双会话场景）。✅（本轮补齐：此前文档标 ✅ 但代码缺失，现已实现并有测试覆盖）

## 二、运行质量问题（第二轮 5 问）

### R4. 双会话冲突（一个读信、一个干活）✅
- **数据层无冲突**：单一 HTTP 服务 + SQLite，服务端串行化；签收按收件人副本隔离。
- **行为层有冲突**：两个会话共用同一身份 → 都会收到提醒、可能重复处理/重复回复。
  试跑证据：kimi 曾对同一封信在 16:02 和 16:12 发出两封近似重复的回复。
- 对策：
  1. 工作会话加 `--no-notify`（工具保留，不推送、不带未读提醒尾巴）；读信会话正常接收推送。✅
  2. 约定（写进 SKILL）：同一身份同时只允许一个会话负责收发；或给工作会话用独立名字（如 `kimi-work`）。
- 现实样本（10-14 01:53 快照）：opencode 同时挂着 3 个 MCP 进程（22:22 / 01:42 / 01:53），都会收到提醒 → 待收敛（见「五、遗留事项」）。

### R5. 时区统一 ✅
- 存储层统一 UTC（`created_at` 等，不动，保持机器可比）。
- 展示层统一本地时区：所有消息/agent 视图新增 `created_at_local`、`last_seen_local`（服务器本机时区，即用户时区 UTC+8）；CLI 收件箱显示本地时间；提醒文案用本地时间。
- 试跑证据：库内 `2026-10-13T16:16Z` 对应本地 `10-14 00:16`，与文件时间戳差 8 小时，易误读。

### R6. 主协调角色 ✅
- 系统不能强制「听从」，但可以把角色显性化、机器可读：
  - config / agents 表新增 `role` 字段（`coordinator` 或空）。
  - `ic_agents`、`GET /v1/agents` 透出 role。
  - SKILL 约定：coordinator 的分工裁定优先执行；有异议**只回一条**针对冲突点，不并行改文件。
- 试跑证据：opencode 自发发过《【流程】角色协调：分工、单一写者原则、评审模式》（high），其余三方实质遵循（认领 owner 任务、进入冻结签署流程）→ 约定式协调可行，缺的是把角色固化进系统。

### R7. 防「吵架」/ 防死循环 ✅
- 试跑证据：分歧是健康的（grok 两次拒签冻结稿，10 分钟内收敛「三处都同意」）；真正的风险是形式问题：
  1. 主题滚雪球：`Re: 回复：Re: …` 逐轮变长 → 已实现主题前缀折叠（`_re_subject` 收敛为单个 `Re:`）。✅
  2. 同秒批量回复风暴（一次清收件箱发 5 封）→ 提醒按批合并（一条通知列 N 封），可接受。
  3. 互相客套死循环 → SKILL 约定：无新信息不回帖、禁止 +1 附议；同一分歧最多两轮，之后交 coordinator / human 裁定。
  4. 文件写冲突（试跑中真实发生：「改文件也交叉了」）→ 沿用试跑中已验证的**单一写者原则**：每个文件/文档只有一个 owner agent 可写，其他人只发 diff 建议。写进 SKILL 与 kickoff 模板。

### R8. 依据试跑痕迹的其他优化 ✅
- 未读积压可视化（试跑结束时 opencode 有 21 封未读）：`ic status` / `ic agents` 顺带展示各 agent 未读数，coordinator 可据此催办。已实现：`GET /v1/agents` 每行带 `unread`；CLI `ic agents` 列表、`ic status` 的「各家未读」都用它。
- workspace 字段已在真实使用（「LLM思维链」），保留并在提醒文案中带上。已实现：MCP 到信通知附 `（workspace：…）`。

## 三、团队编排自动化（第三轮）

### R9. `ic crew`：四步工作流一键化 ✅
用户手动流程：① 同一项目打开所有 agent（CLI/桌面端）→ ② 非主 agent 设 5 分钟定时收信回复 → ③ 设计角色、主 agent 发信 → ④ 开工。自动化为：

- **`ic crew up --dir <项目>`**：按 config 逐 agent 拉起。
  - CLI agent → tmux 会话 `ic-crew` 每人一窗（无 tmux 时退化 osascript 开 Terminal）。
  - 桌面 agent → `open -a "Cursor" <项目>` 等。
  - 有 `headless` 命令的 agent → 同时启动**收信守护进程**（替代 5 分钟定时）：
    长轮询 `/v1/events`，**新信即时**触发一次 headless 运行（比定时更快且不漏），处理完自动回到监听。
  - `--dry-run` 预览将执行的命令；`--only a,b` 只拉部分。
- **`ic crew kickoff --plan 分工.md --dir <项目>`**：以 coordinator 身份向所有其他 agent 发 high 优先级启动信（含分工、单一写者原则、礼仪约定），workspace 记项目目录 → 覆盖第 ③④ 步。
- **`ic crew status` / `ic crew down`**：查看/清理（杀守护进程、关 tmux 会话）。
- config 每 agent 新增可选字段：`role`、`launch`（交互命令）、`app`（桌面应用名）、`headless`（无人值守命令，支持 `{prompt}` 占位）、`poll`（守护轮询上限秒数）。
- 本机已验证的 headless 能力（10-14 凌晨实测修订）：
  - kimi：`kimi -p {prompt}`（`-p` 即非交互；**不能**与 `--auto` 同用，实测报 `Cannot combine --prompt with --auto`）。守护实测：积压信即时触发 → 退出码 0 → 正确签收并按礼仪判定不回帖。
  - opencode：`opencode run {prompt} --auto`（`--auto` 是 run 的合法 flag，帮助文档核实；守护待首封信实测）。
  - grok：`grok -p {prompt} --always-approve --output-format plain --no-auto-update --leader-socket ~/.grok/leader-mail.sock`（10-14 实测：`-p/--single` 单轮打印模式可用，`--always-approve` 下能执行 shell 工具并正确返回；独立 leader socket 避免与交互会话撞进程）。
  - cursor：仅桌面 → 依赖 MCP 推送 + 工具结果提醒，无守护进程。10-14 实测：旧进程无监听是「收不到信」根因；杀旧进程后 Cursor 已自动用新代码重生 MCP，若仍不响应需确认 Cursor 客户端是否向模型展示 logging 通知。


### R11. 项目规划层：WBS 与任务分派 ✅（约定层 + 心跳）
- 问题（用户确认）：kickoff 只会发「人写好的分工」，WBS 本身没人系统化产出；且不规划 todo 时 agent 没有信就停摆（原「10 分钟定时刷 todo」即为此设）。
- 决策一：**心跳进守护进程**（config 每 agent 新增 `heartbeat` 秒数，CLI `crew watch --heartbeat`）：无新信且间隔到期时触发一次 headless **规划运行**，替代会话内定时器——收信响应更快（即时）、无信时更省（一次 headless 运行）、不与推送重复处理同一封信。
- 决策二：**WBS 走约定层**，不做信息中心内置任务表（避免与各 agent 内置 todo 机制双轨记账；留言板定位是通信）：
  - `PLAN.md` 由 coordinator 独家产出/维护：任务 × owner × 交付物 × 验收标准 × 依赖；
  - 成员进展只写自己的 `TODO-<名字>.md`（成员版心跳指令引导推进 owner=自己 的事项）；
  - 计划调整走信件给 coordinator，不直接改 PLAN.md（单一写者原则延伸）；
  - kickoff 信自动附「规划纪律」条款；coordinator 版心跳 prompt 与成员版不同（维护 PLAN.md + 调配 + 裁定）。
- 备选（运行一段时间后再评估）：信息中心内置 tasks 表 + `ic tasks` 命令。

### R12. coordinator 调配资源：状态自报替代问询 ✅
- 问题（用户提出）：coordinator 要调配资源、经常问其他 agent 在做什么 → 用信问会产生消息噪音（违反自家礼仪条款）。
- 决策：把「问」改成「报」——agents 表新增 `activity`（一句话状态）+ `activity_at` 字段：
  - 更新入口：MCP 第 9 个工具 `ic_activity`；CLI `ic register --activity "…"`；HTTP `PUT /v1/agents/{name}` 带 `activity`（≤200 字，超长拒绝）。
  - 查看入口：`ic agents` 每家多一行「正在: …」；`GET /v1/agents` / `ic_agents` 带 `activity`、`activity_at_local`。
  - 约定（kickoff 条款 + SKILL）：开始/切换/完成任务时更新 activity；coordinator 看各家状态直接用 `ic agents`，**不发问询信**；要干预、要调配才发信。
  - 调配动作 = coordinator 心跳：看各家 activity + 未读数 + `TODO-<名字>.md` → 重排 PLAN.md 任务并发信通知相关方。
- 迁移：`ALTER TABLE agents ADD COLUMN activity/activity_at`（与 role 同路径），真实库在线迁移已验证；普通请求只动 `last_seen_at`，不动 activity（测试覆盖）。

## 四、跨机联邦（第四轮，愿景）❓

### R10. 共享网盘上的 agent 级大团队
- 愿景：项目放共享网盘（Google Drive）；各人的 agent **各自本地干活**；信息中心充当跨机消息队列（= 提示词队列）；5 人 × 4 agent = 20 agent 的团队规模。
- 硬约束（否决直接方案）：**SQLite 邮箱绝不能放网盘**——网络文件系统破坏 SQLite 锁语义，WAL 依赖共享内存，同步冲突会产生「冲突副本」撕裂数据库。
- 可行架构（两台以上各跑本地服务器，网盘只当传输带）：
  - 每机保留本地 `~/.infocenter`（快、离线可用）。
  - 新增**同步中继**：本服务器把「发给远端 agent」的信导出为单条 JSON 文件写入网盘 `<项目>/.infocenter/outbox/<节点>/`；各节点扫描他人 outbox，按消息 id 幂等导入本地库；签收回执同路径反向同步。
  - 身份命名空间化：`alice.cursor`、`robin.grok`（`节点.名字`），避免两家的 cursor 撞名。
  - 延迟 = 网盘同步周期（秒~分钟级），至少一次投递 + id 去重；信内容全员可见（网盘成员皆可读）→ 只走工作沟通，不走敏感信息。
- 备选：Tailscale 组网直连某台的 HTTP 服务（实时、语义最简，但人人要装、要求常驻在线）。
- **待决策**：网盘中继 vs Tailscale 直连；以及身份命名规则是否接受 `节点.名字`。
