## 一、执行摘要

**一句话定位**：把执行与账本解耦——agent 留在各自最适配的 harness 里干活，彼此只交换**信件、案卷、仓库文件**三种共享物；由一层很薄的服务中心集中记账。同一套软件递归装三层（个人 → 部门 → 企业），每层只向上暴露**一个代表 agent**。

**三个关键判断**

1. **卡点不在模型能力，在协调层缺位。** 据 Gartner（2026-04）测算，到 2028 年财富 500 强企业平均可能运行超过 15 万个 agent，而仅约 13% 的组织自认治理到位。沸腾的不是智能，是账。
2. **胜负手是"薄"，不是"厚"。** Microsoft Agent 365（2026-05 GA）、AWS Agent Registry（2026-08 GA）、Salesforce Agent Catalog 与 AgentExchange，方向惊人一致：把 agent 收进自家运行时，再治理。本报告取舍相反——**不接管运行时，只接管契约**。这一条同时决定了架构形态与导入阻力：组织结构不用动，人从执行者退到管理者。
3. **案卷是市场留白。** A2A 定义了 `task`，却把"这件事现在办到哪、谁验收、谁担责"留空。而"工单 + 审计 + 信誉"三合一的案卷，恰是决策者最想要、也最难自建的那一层。

**结构导览**：第二章拆解 agent 落地为何卡住；第三章把"执行去中心、账本集中"讲透并给出退化反例；其后依次展开三层递归与代表 agent、组织与责任的再分配、技术架构与防篡改留痕、市场先例与差异化站位、商业模式、落地路线与风险治理。

## 二、背景：为什么 agent 落地卡住

**一、harness 异质，注定无法共用运行时。** 一台机器上同时开 Grok、Kimi、OpenCode、Cursor、omp 已是常态，而它们的"干活方式"没有一处相同：Kimi 的 `-p` 与 `--auto` 互斥；`cursor-agent` 不带 `-f` 会被目录信任确认拦死；Grok 需要独立的 leader socket 才不与交互会话抢进程；omp 必须 `--no-session` 才不自动接续旧会话。这还只是启动命令层面；prompt 组织、工具集、记忆格式、上下文管理更是各家私事。结论很直接：**要求大家统一到某个平台运行时，等于要求所有人放弃自己最强的那一面**——这正是多数 agent 平台被抵触的根因。

**二、协调成本不在消息量，在"消息没有状态"。** 本地实测库里有数十封真实往来：同一份请求曾被两个会话发出近似重复的回复；一个身份一度积压二十余封未读；同一身份挂了三个进程，各自重复处理同一封信。异步留言解决了"说一句话"，但"这句话之后这事归谁、办到哪"无人记录。**信是短期记忆，用信当账本必然乱。**

**三、没有留痕，就没有验收与审计。** 交付物落在文件里，决策落在对话里，改动落在 git 里，三者对不上号。append-only 的收件箱不等于审计凭证——它只证明"有人说过"，不证明"谁批准、依据什么、是否被改过"。缺哈希链或签名，"流程可审计"就是纸糊的。

**四、组织不敢把活交出去，根因是责任不能外包。** 一个部门把活交给 agent，最先问的不是"它多聪明"，而是"出事谁担责、我怎么证明它照办了"。多数企业不缺能干活的 agent，缺的是一条**可问责的证据链**。

## 三、核心论点：执行去中心、账本集中

**原则**：执行（谁用什么 harness、怎么干活）彻底去中心；账本（谁在办、办到哪、谁验收）集中一处说了算。由此推出唯一硬约束——**只共享契约，不共享运行时**。共享物只有三样：信件（纯文本）、案卷（极简结构化节点）、仓库文件。prompt 怎么写、用哪些工具、记忆怎么存、内部数据格式长什么样，全是各家私事，中心不碰、不看、不规定。

| 解耦 | 做法 | 收益 |
| --- | --- | --- |
| 能力 ↔ 通讯 | agent 管能力，中心只管通讯 | 用最强 harness，不被平台规定怎么干活 |
| 执行 ↔ 留痕 | 干活各自为政，留痕统一登记 | 天然形成流程与结果审计 |
| 组织 ↔ 协作 | 部门管自己的 agent，中心定统一契约 | 各部门专注自己的 agent |
| 执行 ↔ 组织 | 组织结构不动，只改"谁来干" | **不必改组织，只改执行者** |

**这一条原则同时解释了另外三件事：**

1. **为什么主办必须去中心。** 谁接到活谁主办，而不是中心派单。中心一旦派单，就必须知道每个 agent 能干什么、忙不忙、成本多少——它立刻开始建模执行，解耦崩。去中心主办只需一条极简规则：认领写进投递记录，按 thread 传播。
2. **为什么案卷必须持久化。** 账本的价值全在时间维度。会话结束、运行时上下文消散，但"当前状态 + 每个经手人的一行批示"必须留下来，成为工单、审计、信誉的共同底座。**信是短期，案卷是长期。**
3. **为什么服务中心要"薄"。** 薄不是风格，是机制前提。中心只做通讯 + 账本 + 协调；一旦开始编排、调度、托管，就是在重新规定 agent 怎么干活。

**反例：中心变厚会怎样退化。** 设想服务中心"顺手"接管任务编排：它会要求 agent 上报细粒度能力、回报执行进度、按中心的 DAG 走。三步之内，差异化的 harness 被压平，各家的 prompt 与工具被中心格式绑架；部门不再愿意升级自己的 agent（升级要重新过中心的兼容性），"每层专注开发自己的 agent"这一最大红利随之蒸发。麦肯锡的 agentic mesh 方向与本报告一致（其"发现"能力的目标正是"让系统使用 agent **而不必知道它跑在哪个 runtime**"），但它把答案做成了又一层协调运行时；本报告的取舍是：协调只发生在契约上，运行时不发生协调。

| — | 薄（本报告主张） | 厚（退化路径） |
| --- | --- | --- |
| 中心知道什么 | 信、案卷节点、契约字段 | 各家能力、进度、成本、DAG |
| agent 自由度 | 自带 harness，自主决定怎么干 | 按中心格式与流程干 |
| 部门升级 agent | 随时，互不影响 | 每次都要重新适配中心 |
| 失败形态 | 中心挂了，各层仍能各自干活 | 中心一插手执行，解耦不可逆 |

## 四、分层模型：逐层接入（个人 → 部门 → 企业）

这一节回答部署形态：这套系统不是"建一个平台服务全公司"，而是**同一套软件装三层**，每层自治，层间只留一个代表 agent 当接口人。它是整个设想里唯一新增的"结构件"，也是把"个人做的小工具"变成"企业能落地"的关键。

### 4.1 结构：三层递归，一层一跳

```
企业层      企业服务中心        ← 全企业账本 + 通讯
               ▲
               │  接入：企业战略级 agent              ← 一跳
               │
部门层      部门信息中心 ── 部门主 agent   ← 本部门账本 + 通讯
               ▲
               │  接入：个人 PA                      ← 一跳
               │
个人层      个人信息中心（单机版）── 个人 PA
               └── 整合本人的若干 agent（grok / kimi / opencode / cursor…）
                    每个 agent 留在自己最适配的 harness 里
```

规则只有一条：**每层只向上一层暴露一个代表 agent**。个人 PA 只跟"本部门主 agent"说话，部门内部的其它 agent 它既看不见也不需要看见；部门主 agent 只跟企业战略 agent 说话。跨层**永远只是一跳**。递归的含义是：个人层怎么整合自己的 agent，部门层照做；部门层怎么整合，企业层照做。

### 4.2 为什么不需要全局层级地址

平铺的 A2A 点对点模型里，N 个 agent 两两可达，"谁适合干这件事"就必须靠一个**全局注册表**来发现。目录随节点数增长，本身变成新的中心与攻击面，而且为了被找到，每层组织细节和能力全集都得先曝光。本模型把发现**收敛到"上一层只见下一层的代表"**：你只需知道"我的上一层代表是谁"（配置里一条登记），不需要 `企业.部门.人.agent` 这种全局路径。组织怎么变、层内换谁、换什么工具，都只影响本层，不外溢。

| 维度 | 平铺 A2A（点对点 + 注册表） | 逐层接入（代表 agent 一跳） |
| --- | --- | --- |
| 发现 | 需要全局注册表，人人可查 | 只认上/下一层的代表，配置一条 |
| 地址 | 需全局唯一定址 | 层内局部命名，跨层只认"代表" |
| 变更外溢 | 换人/换工具要更新目录 | 层内自变，上层无感 |
| 暴露面 | 组织细节与能力全集外泄 | 只暴露代表及其声明 |
| 治理 | 中心目录成为瓶颈与单点 | 责任分层到各层，各管各的账本 |

这也正是既有决策"身份名恰好一个点"仍能成立的原因：**命名与寻址按层局部化**，不必为一个从不出现的全局地址推翻既有设计。

### 4.3 代表 agent / 网关的设计要点

代表 agent 既是接口人，也是信息闸门，必须当"网络设备"而不是"又一个聊天机器人"来设计：

- **身份**：每层唯一、可签名（对齐 A2A 的签名 Agent Card）。它代表"这一层"而非某个人——部门主 agent 换实例，企业侧只改一条登记，身份不变。
- **能力声明**：只声明**对外的可委托能力**，不是本层 agent 的全集。内部会写代码的 agent 不外露，只暴露"代码评审"这类服务条目。
- **信息闸门**：默认只向上报三类——任务/案卷编号与状态、需要的资源或决策、交付物指针。原始私信、中间过程、个人数据一律留层内。闸门是**配置项**，不是代码，改闸门不动系统。
- **权限边界**：明确代表能替本层承诺什么（接单、拒单、合并），不能做什么（不经人批准动用预算、不替下属 agent 承诺对外交付）。
- **断联与容灾**：代表是单点，三招兜底——信与案卷落在**本层账本**，代表挂了不丢；上层只感知"该部门代表离线、任务滞留"，**不级联失败**；代表可替换，靠签名保证"换实例不改身份"。

### 4.4 同一套软件递归部署

三层不是三套产品，而是同一个"信 + 案卷 + 服务中心"的三种部署规模。**跨机的联邦中继，就是"向上接一层"的运输工具**：本节点把要出层的信导出为 JSON，写进共享目录的 `outbox/<节点>/`，对端按消息 id 幂等导入本地库，回执反向同步。一次中继 = 一次层间接入。

| 层 | 部署规模 | 代表 agent | 与其它层的差异 |
| --- | --- | --- | --- |
| 个人 | 单机、单进程、一个 SQLite | 个人 PA | 无鉴权需求；隐私边界＝本机 |
| 部门 | 联邦（多机 + 共享目录中继） | 部门主 agent | 需要闸门策略与成员名单 |
| 企业 | 联邦的联邦（多部门主 agent） | 企业战略级 agent | 需要签名身份、跨层审计 |

### 4.5 一个例子：周报是怎么一层层上去的

- **个人层**：Alice 的 PA 整合了写代码的 agent 与查资料的 agent。周五她说"把本周三个项目的进展汇总成一页周报"。PA 在本层干活、产出草稿，只把"周报草稿 + 文件链接 + 需要她补的一处数据"报给部门主 agent。私聊、草稿中间版本、客户的吐槽，都不出层。
- **部门层**：部门主 agent 收齐 8 人的摘要，合并成部门周报，顺手裁定冲突（有人报 80%、另一处说延期）。它自己解决不了的两件事升级上去——但**只上"部门周报 + 两条待决问题 + 案卷编号"**，不上 8 份原文。
- **企业层**：企业战略 agent 只看到几个部门主 agent 的周报与升级项，于是能做跨部门协调：发现 A 部门卡在 B 部门未交付的接口上，直接派单回 B 部门主 agent。

全程三次交互，每次一跳；每层各自留痕。事后谁想追溯"我的周报怎么进的公司周报"，沿案卷编号就能一路查到——这正是"账本集中、执行去中心"在结构上的样子。

## 五、组织含义：管理结构不变，人人都是管理者

如果只能留一句卖点，是这句：**这套东西不需要动组织**。汇报线、预算科目、职责边界、审批链一律不变，变的只是"具体的活谁来干"。相比之下，多数平台类方案暗含一次组织改造——新设数字化岗位、重画流程、把 agent 收进平台自己的运行时。**把一次组织变革降级为一次"工具更换"，对决策者的价值远大于技术先进性。**

| 角色 | 干什么 | 变了吗 |
| --- | --- | --- |
| **人（管理者）** | 定目标、分配资源、派活、验收、**担责** | 内容变了，位置没变 |
| **agent（执行者）** | 干活，留在自己的 harness | 新增的"编制外劳动力" |
| **服务中心** | 通讯 + 账本 + 协调，不碰执行 | 新增的基础设施 |

**三个推论：**

1. **导入阻力小。** 不用动组织、不用改流程、不用人人学新工具。可以先在一个人身上跑通，再在一个部门跑通，不必全公司同时切换，也不需要成立"转型办公室"——这正是"个人层是种子层"的组织版本。
2. **责任仍在人。** agent 是"编制外员工"，干活可以外包，**担责不能外包**。谁派的活、谁验收、谁签字，责任落在人。于是可信留痕不是合规加分项，而是**前提**：案卷必须 append-only 并加哈希链/签名，否则这套东西不能用在任何有责任的场景。
3. **人的新核心技能是"规划资源 + 验收"。** 定目标、给预算与时间、派活、判断交付物是否达标；写代码、查资料、做表交给 agent。这也意味着**每个人都是管理者**，管理幅度从"带几个人"扩展为"带几个 agent"。

**对 HR / 绩效 / 预算的潜在影响，宜早定规则：**

| 问题 | 建议口径（需拍板） |
| --- | --- |
| 绩效怎么算 | 考核从"做了多少活"转向"目标达成、资源利用率、验收质量" |
| agent 产出归谁 | 归派活的人/团队，agent 不作为产出主体，责任链才闭合 |
| 预算形态 | 由人力编制扩展到组织内的**算力/额度预算**，可能催生内部算力租赁科目 |
| 出错谁担责 | 推定派活人担责；越权承诺由权限边界阻断 |
| 跨层泄露如何界定 | 闸门策略由谁审批；越层数据默认不外流 |

**一个人身上的前后对比**：某项目经理的一天——改造前，他花三小时写周报、挨个催四位下属的进度、在三个群之间搬运结论；改造后，这些由 agent 之间直接流转，他只剩两件事：早上把本周目标与资源交代清楚，傍晚验收交付物并把不合格的打回重做。**工作量没有减少，而是从"动手"移到"判断"**——而判断恰恰是他本来就该做、却长期被杂事挤掉的那部分。

**两处边界（不适用场景）**：① **强实时协同不适用**——信与案卷是异步的，适合"派活—交付"节奏，需要毫秒级同频的现场联动（如线上应急值守）不能靠它；② **统一强制策略，闸门比协调更重要**——安全、合规这类必须全员一致执行的要求，应作为契约下发给每层代表，而不是靠层间协商。

## 六、技术架构

### 6.1 分层契约：四层单向依赖

解耦不能靠口号，必须落到"层间只经明确定义的接口耦合、不许反向渗透"。

| 层 | 职责 | 落地接口 | 明确不做 |
| --- | --- | --- | --- |
| 协议层 | 信件往返：收发、线程、开销 | HTTP `/v1/messages`、`/v1/threads/{id}`；MCP 九工具；对外可包 A2A Message | 不解释"活干到哪一步" |
| 状态层 | 办事追踪：案卷/工单、认领、收局 | `cases` / `case_nodes`；`GET /v1/cases`、`POST /v1/cases/{id}/{pause,resume,abort,close}` | 不管谁来干、怎么干 |
| 传输层 | 跨机/跨层搬运 | 联邦中继 `<项目>/.infocenter/outbox/<节点>/` JSON；`X-Window` 头透传 | 不做语义转换 |
| 治理层 | 注册、发现、权限 | `config.json`（Agent Card 式条目）、`windows` / `projects` 视图 | 不托管运行时 |

**唯一硬粘合点**：协议层与状态层共用 `thread_id`——**信是正文，案卷是索引**，两者绝不互相复制内容。这条纪律是"薄"的护城河：服务中心能读信、能记账，但不能替 agent 干活。

### 6.2 数据模型（表级）

- `projects`：`workspace`(PK，项目目录) / `name` / 时间戳。一栋楼。
- `windows`（办公室，临时）：`window_id`(PK，如 `w-3f2a91`) / `agent` / `workspace` / `state`(默认 `active`) / `activity` / `activity_at` / `pid` / 首末时间 / `left_at`。**activity 按办公室分区**，解掉同一身份多项目互相覆盖。
- `cases`：`id`(PK) / `thread_id`(**UNIQUE**，一问题一案卷) / `title`(取自首封来信主题) / `workspace` / `status`(`pending｜open｜paused｜aborted｜done`) / `owner_agent` / `owner_window` / `waiting_for` / `sealed`(0/1) / 时间戳。**"待谁"由 `waiting_for` 表达，不额外占状态位。**
- `case_nodes`（**append-only**）：`id`(自增) / `case_id` / `agent` / `window_id` / `action` / `note` / `status` / `auto`(0/1) / `created_at`，索引 `(case_id, id ASC)`——顺序即时间线。
- `deliveries`（认领载体）：PK `(message_id, to_agent)`，加 `claimed_by` / `claimed_at`；旧库用 `PRAGMA table_info` 查列、缺列即 `ALTER TABLE ADD COLUMN` 迁移，新表 `CREATE TABLE IF NOT EXISTS`。

节点格式固定为一行：`<时间> · <经办 身份/办公室> · <动作> → <结果>`。系统补写节点 `auto=1`，渲染标 `[自动]`，与人工批示区分。**封卷只读**：`aborted`/`done` 置 `sealed=1`，此后一律拒绝追加；要接着办只能发"再开信号"重开。

### 6.3 窗口与认领

病根是"系统只认名字，不认窗口"，表现为重复回信、未读错乱、activity 覆盖。处方：给每个窗口一个内部编号——来源优先 `INFOCENTER_WINDOW`，否则自动生成，随 `X-Window` 头下发。**名字空间不动**，对外仍是一个身份。

```
未认领 ──认领──▶ 在办(open) ──▶ 待谁(waiting_for) ──▶ 办结(done)  ┐封卷
                    │  ▲                                             │
                  暂停(paused)                         中止(aborted) ┘封卷
                    └──▼ 恢复
```

- **先到先得**：条件更新 `UPDATE deliveries SET claimed_by=? WHERE message_id=? AND to_agent=? AND (claimed_by IS NULL OR claimed_by=?)`；影响行数为 0 即"已被其他窗口主办"，不硬锁、不死锁。
- **按线传播**：认领落在 `thread_id` 上，同线程后续信不再推给别的窗口。
- **软认领**：只标记 + 提示，可 `--force` 接手。
- **去中心化立案**：谁先接到新线程谁立案，即为主办；该线程内它说了算，全局 coordinator 只管跨事务总盘子。
- **推送过滤**：`since=0` 补报与被认领的线都按窗口过滤；未读尾巴只计"未归属其他窗口"的信，做到"同身份两窗口只提醒一个"。

### 6.4 向后兼容与失败边界

| 边界 | 行为 |
| --- | --- |
| 无 `X-Window` | 不认领、不过滤，逐条等价旧版，旧客户端零回归 |
| 办公室正常离场 | 主动上报 → 自动归入中止 + 封卷 + `[自动]` 节点 |
| 崩溃/断电 | **不做超时扫描**；下次有人触及该线时才惰性补齐"离场→中止→封卷" |
| 并发认领 | 条件 UPDATE，先到先得，败方收到"已被主办"提示 |
| 同窗口重读 | `claimed_by == 自己` 不算冲突 |
| 广播信 | 认领记在 `(message_id, to_agent)`，天然按收件人隔离 |

"暂停要快"的代价要认账：打断当前轮可能留半成品，靠案卷补记一行断点兜住，不假装没发生。

### 6.5 审计与防篡改

`append-only` 只保证"只追加"，不等于"不可篡改"——本地文件可被改写，只靠自增主键当审计凭证是纸糊的。落地建议：

1. **哈希链**：`case_nodes` 补 `prev_hash` / `hash` 两列，`hash = H(case_id ‖ seq ‖ agent ‖ window_id ‖ action ‖ note ‖ status ‖ auto ‖ created_at ‖ prev_hash)`。
2. **每案 Merkle 根**：办结时把该案节点哈希汇总成根，写回 `cases`。
3. **签名**：根由主办窗口密钥签，复核方副签；身份锚点复用 A2A 的签名 Agent Card。
4. **锚定**：把 `(case_id, root, 签名, closed_at)` 导成回执写进 `outbox/<节点>/receipts/`，随联邦中继形成跨机副本。
5. **校验**：`ic case` 顺链验哈希，任何单点改库都会断链暴露。

### 6.6 与 A2A 的关系：兼容而非自造

A2A 已把"异质 agent 互通"标准化。本方案不去替代，只在其留白处落座：

| A2A 对象 | 本方案对应 | 说明 |
| --- | --- | --- |
| Agent Card | `config.json` 条目 | 身份/能力/角色 ↔ card；`launch`/`headless` 是本地私有运行时，**不导出** |
| Task 生命周期 | `case` + 状态 | `input-required` ≈ `待谁`，`canceled` ≈ 中止，`completed` ≈ 办结 |
| Message / 状态更新事件 | 信件 / `case_node` | 消息是正文，节点是索引 |
| Artifact | 节点里的交货引用（diff、commit、文件） | 只存引用，不搬运内容 |

粘合键即 `thread_id`（对应 A2A 的 `contextId`）。A2A 刻意只标准化"单次任务怎么谈"，把**跨任务的编排、账本、信誉、部门治理**留空——**那正是本方案的落点**。

## 七、市场调研：先例与格局

这一层（协议／注册表治理／市场／理论）在 2025–2026 被大厂迅速占满。下面逐一核对各自的能力边界与留白——那正是机会窗口。

### 7.1 协议层：分工已定，审计是留白

- **A2A（Agent2Agent）**：Google 于 2025-04 发起，2025-06 捐给 Linux Foundation。据其 2026-04 一周年公告：150+ 组织支持、22,000+ GitHub stars、五语言 SDK，已深度集成 Google、Microsoft、AWS。2026-03 发布 v1.0 稳定版，v1.0.1（2026-05）为当前稳定版；v1.0 起引入**签名 Agent Card**（JWS 分离签名）与支付协议 AP2。Agent Card 本就是机器可读的能力声明，**几乎就是 `config.json` 条目的标准化版本**。
- **MCP（Model Context Protocol）**：Anthropic 起、同归 Linux Foundation，核心协议已转为无状态。两者分工已被官方钉死：**A2A 管 agent↔agent 跨组织协调，MCP 管 agent↔工具/数据**。
- **留白（关键）**：两套协议都不定义审计。据 Kang & Diponegoro（arXiv:2606.31498, 2026-06）以六维治理分类评测五个协议：**投票与异议保留在所有协议中普遍缺失；A2A 仅在"成员"上得 Partial，其余治理维度（含审计/重放、人工升级）均为 Absent**。A2A 只签 Agent Card、不逐条签名消息信封，鉴权"委托给部署方"；MCP 路线图亦把审计、SSO、网关列为"扩展而非核心规范"。**A2A 刻意留白的那一层，正是"案卷（工单+审计+信誉）"该占的位置，至今无人填。**

### 7.2 注册表治理层：大厂已占据"中心化控制平面"

- **Microsoft Agent 365**：2026-05-01 GA，$15/用户/月。核心是集中注册表 + 生命周期治理（安装/发布/封禁/删除/改派 owner）+ 规则化治理（自动过期不活跃 agent、自动改派无主 agent），身份底座是 Entra Agent ID。其 **registry sync** 可把 AWS Bedrock、Google Cloud 等平台上的 agent 拉进同一注册表。
- **AWS Agent Registry（AgentCore）**：2026-04 预览、2026-08 GA。私有治理目录，覆盖 agent / tool / skill / MCP server；可按事业部开多实例、各带审批流；CloudTrail 审计、IaC、跨账号共享；本身可作 MCP server 供 IDE 查询。AWS 自陈它"不在调用路径上"——只是**目录平面**。客户 Southwest Airlines 用它做企业级 agent 目录。
- **Salesforce Agent Catalog / Google Gemini Enterprise**：同类，IT/安全侧的中心注册表，供"启用/禁用、审计、库存"。
- **能力边界（诚实说法）**：这些产品都假设**统一身份与统一控制平面**，本质是"把你的 agent 收进它的平台来治理"。它们给的是**自上而下的 IT 视图**，不是跨异构 harness 的对等契约，也不解决"谁在办、办到哪、谁验收"的**办理账本**。

### 7.3 市场层：公开侧饱和，企业内部侧空白

- **公开市场**：Salesforce **AgentExchange** 在 2026-04 把 AppExchange、Slack Marketplace、Agentforce 目录三合一，上万条列表、统一计费 + 安全审查；OpenAI 的 **Apps in ChatGPT / Apps SDK** 让第三方 app 进对话；Google **Agent Marketplace**；Microsoft Marketplace。
- **加密 / DePIN**：Fetch.ai（ASI Alliance，含 SingularityNET、Ocean）的 Agentverse；Render（租 GPU）；Bittensor/TAO（子网经济）；io.net（GPU 云 + "model & agent marketplace"）。市值量级约十亿美元级。
- **评估**：公开市场已饱和且被平台绑定；加密圈完成的是"**无许可、面向个人**的算力/模型租赁"，但 **企业内、组织内、带责任链的算力/agent 租赁基本空白**——DePIN 没有雇主/部门/责任归属语义，也难过合规审计。

### 7.4 理论层：需求侧已被分析师讲透

- **O'Reilly《Agentic Mesh》**（2026）：核心组件正是 agent registry、marketplace、信任构建机制、human-in-the-loop。
- **McKinsey**（2025–2026）"agentic mesh 七能力"：发现、AI 资产注册表、可观测、鉴权授权、评测、反馈、合规与风险——与要补的件几乎一一对应。
- **Couchbase《The Platform Harness》**（2026）：提出"平台 harness"是"缺失的一层"，佐证"harness 决定 agent 上限"。
- **需求侧数据**：Gartner（2026）预测 2028 年 Fortune 500 平均用 15 万 agent、仅 13% 治理就绪；IBM IBV（2026）称 94% 企业认为 sprawl 抬高安全风险；Salesforce 基准称平均企业用 12+ agent、约半数为各自为政。

### 7.5 关键核对：企业内"分层信息中心 + 部门专注自研 agent"是否已有人做？

**做了，但方向不同，我们的组合仍是空白。** 三点：

1. **"internal agent marketplace" 有人做**：有的企业已在交付、质量、IT、营销、法务、HR 复用内部 agent 目录。但它们是**雇主面向员工的批准目录（approval gate）**，解决"哪个 agent 可用"，不解决跨部门对等办理与追责。
2. **部门专注自研 agent 是现状**，但治理被动：逐平台治理造成重复劳动、安全风险与成本失控；"marketplace 只是可见层，底下必须有 registry + 身份 + 政策网关 + 可观测 + 生命周期"。身份侧仍是真空——多数企业用共享 API key/服务账号，仅少数把 agent 当独立身份。
3. **没人做成的**：① 把"个人 → 部门 → 企业逐层接入、每层只暴露一个代表 agent"做成机制；② 组织不变、人从执行者变管理者；③ 把工单+审计+信誉做成 A2A 留白层的**协调底座**。

## 八、差异化定位与竞争分析

### 8.1 四个差异点

1. **harness 异质是一等公民。** 大厂产品的默认动作是"把 agent 收进我的 builder / 运行时"。本方案反其道：**agent 留在自己最适配的 harness，只共享契约**；执行彻底去中心、账本集中。
2. **案卷 = 工单 + 审计 + 信誉，正好填 A2A 的留白。** 据前述治理评测，审计/人工升级/异议保留是所有协议的 Absent 项。我们把"谁在办、办到哪、谁验收、信誉几何"做成一条 append-only 的共享时间线——这是**协议层刻意不做、平台层又只在其围墙内做**的那块。
3. **部门层级 + "逐层接入 + 组织不变"。** 大厂给的是自上而下 IT 视图；我们给的是**递归同构机制**：个人 PA 接入部门、部门主 agent 接入企业，每层只暴露一个代表 agent（网关 + 信息闸门），组织结构不动、人从执行者变管理者。
4. **企业内部算力/agent 租赁。** DePIN 已证明无许可租赁可行，但**企业内、带责任链的租赁空白**。我们不需要代币，只需案卷里的信誉 + 计费 + 鉴权。

**已被占据 vs 尚是空白**：已被占据的是——协议标准（A2A/MCP）、云厂商的中心控制平面与注册表、面向 C 端的公开市场与商业闭环。仍是空白的是——**跨异构 harness 的对等契约层、协议留白处的办理账本、逐层接入的组织落地路径、企业内部带责任链的租赁**。本方案把资源全部压在空白侧，对已被占据的部分一律"兼容/登记"而非"重造"。

### 8.2 SWOT

- **优势（S）**：定位在协议留白处，不与大厂正面竞争；单机闭环已可运行；异质 harness 是真需求；"组织不变"导入阻力小。
- **劣势（W）**：目前仅单机/单人多 agent，缺注册表、防篡改留痕、鉴权/计费/沙箱；产品体量远小于大厂；中心与代表 agent 皆为单点。
- **机会（O）**：治理需求已被分析师讲透，企业正从"造 agent"转向"管 agent"；A2A 留白短期无人填；企业内部侧、逐层接入侧仍空白。
- **威胁（T）**：**标准引力**——A2A/MCP 一旦补上审计扩展，案卷恐被"规范吸收"；**大厂生态吞噬**——registry sync 把跨厂商 agent 收进单一控制平面；以及"薄厚滑落"使服务中心退化回平台。

### 8.3 站位建议

1. **兼容 A2A，不自造协议**：Agent Card ↔ config 条目、A2A task ↔ 案卷节点，做 A2A 的**扩展/适配层**而非替代品。
2. **切在 A2A 留白层**：编排 + 案卷/信誉 + 部门治理；把"审计/异议/人工升级"作为可插拔扩展贡献回社区，既降低标准引力风险，又占住生态位。
3. **先做厚个人层种子**：对企业侧主动做"向 Agent 365 / Agent Registry 登记"的适配器——**不与之争注册表，而做它的账本层**。
   一句话取舍：**协议兼容、账本自建、注册表借用、市场只做企业内部侧。**

## 九、商业模式与计费设想

### 9.1 计价单位：以"整个 case 承包"为主

| 方案 | 优点 | 缺点 | 定位 |
| --- | --- | --- | --- |
| 按 case 承包 | 与责任、验收、审计同构；买方一眼报价 | 范围易膨胀，需封卷界定 | ✅ 主计价单位 |
| 按轮次/算力 | 精细、易计量 | 把成本风险转给买方，激励"多跑几轮"；与"验收交付"脱节 | 仅作成本线与熔断 |

推荐：**以 case 为结算单元，轮次/算力做内部成本线与熔断阈值**。理由是案卷天生就是一张可封口的账本——`立案 → 办结` 即一张可结算的封套；节点就是里程碑，天然支持分期（认领预付、办结尾款）；中止时按已落节点部分结算，不需要另建一套计量台账。流程：立案报价 → 主办承包 → 里程碑分期 → 办结封卷触发结算 → 中止按节点折价。

### 9.2 企业内部 vs 跨企业

- **部门间结算**：本质是预算/内部转移价格，不涉合同与法律，重点在**配额、优先权、排班**。信誉分直接决定谁先接单、能否接高价值案。风险低，应在单机种子层跑通后再推。
- **跨企业（租赁）**：需要合同、结算通道、担保与合规。此时案卷的**防篡改证据（哈希链 + 签名）从"锦上添花"变成"准入门槛"**——没有可验证留痕，没人敢把活外包。A2A 生态已出现 AP2 等 agent 支付协议可直接对接；而权限与信息过滤（网关 agent）决定什么能外发、什么必须挡在门内。

### 9.3 信誉分：从案卷自然派生

```
信誉   = w1·办结率 + w2·复核通过率 − w3·中止率 − w4·返工率
办结率   = done / (done + aborted)      # 案卷是否收得干净
复核通过率 = 一次通过 / 复核总数          # 交付质量（复核方副签）
中止率   = aborted / 立案总数            # 主办稳定性
返工率   = 被复核打回的节点 / 总节点
```

全部取自 `cases.status` 与 `case_nodes`；`[自动]` 节点用于区分"系统补齐"与"人为失误"，不计入负面。这套指标既是排班依据，也是跨企业租赁的定价系数。附带效果：信誉与留痕绑定后，指标**无法靠自报刷分**，只能靠真实办结累积，形成"干得好→接好活"的正循环。

## 十、落地路线图

整条路线遵循一条铁律：**执行去中心，账本集中；只共享契约，不共享运行时**。三层递归不是三个产品，而是**同一套软件装三次**，因此必须自下而上、逐层验证，绝不跳级。

### 阶段一：个人信息中心（单机闭环）

- **范围**：单机、单人多 agent。信件（通讯）+ 案卷（办事追踪）+ 应用（管理台）+ 跨机联邦雏形。
- **关键交付物**：质量基线（33 项测试零告警全绿）；跨机联邦 v1（网盘 JSON 中继、单点命名、SQLite 绝不上网盘）；窗口·案卷·应用（认领防重复、案卷状态机、三视图管理台可暂停/中止/办结、立案、设定项目地址）。
- **验收（Go/No-Go）**：同身份两窗口新信只提醒一个；一条线不被重复处理；案卷从立案到结案节点完整、一行一节点、封卷只读；办公室离场自动中止并补 `[自动]` 节点；旧库升级不炸、无窗口号行为不变。
- **依赖**：无外部依赖，可立即推进。

### 阶段二：部门层（多机联邦 + 代表 agent 网关 + 注册表）

- **范围**：把阶段一的联邦中继升格为"向上接一层"的正式通道，每层只暴露**一个代表 agent**。
- **关键交付物**：① 代表 agent（网关）——个人 PA 接入部门、部门主 agent 接入企业，兼接口人与**信息闸门**；② 注册表——Agent Card 式的身份/能力/接口声明，字段与 config 条目对齐；③ 一跳寻址——命名与寻址局部化，跨层只跟相邻层的代表打交道。
- **验收（Go/No-Go）**：两个部门各跑一台实例，经代表 agent 完成一次跨机派活与回执；网关能按规则过滤双向信息；注册表能查到一个部门的代表与其能力声明。
- **依赖**：阶段一冻结；联邦稳定。

### 阶段三：企业层与市场（鉴权/计费/沙箱/信誉）

- **范围**：企业级服务中心 = 通讯 + 账本 + 协调，**仍不碰执行**。
- **关键交付物**：统一鉴权与身份目录；审计导出；算力/agent 租赁的计费与沙箱隔离；基于案卷历史沉淀的**信誉**。
- **验收（Go/No-Go）**：企业能回答安全第一问——"谁在调用、调用凭据、操作可否审计、能否零信任隔离"；一笔跨部门协作可完整审计并计费。
- **依赖**：阶段二稳定；**合规先于市场**。

> **为什么必须先做单机闭环**：它是**种子层**。三层的软件、契约、案卷格式完全相同，个人层怎么整合 agent，部门层照抄。更重要的是——**案卷与信誉的全部样本都从这一层产生**：没有真实的"谁认领、谁主办、谁复核、办没办结"的留痕，上层的审计与信誉就是无源之水。跳过单机直接做企业，等于在没有样本的地基上盖楼。

## 十一、风险、治理与合规

| # | 风险 | 缓解措施 |
| --- | --- | --- |
| ① | **薄厚滑落**（最大敌人）：中心被要求做编排、调度、托管，每变厚一次就重新规定 agent 怎么干活 | 把"只共享契约、不共享运行时"钉成红线；新增能力一律归 agent 侧；评审任何中心功能先问一句"这是在替 agent 干活吗" |
| ② | **代表 agent 单点与信任聚焦**：它挂了整层断联，且兼接口人与闸门 | 网关**无状态、可替换**；过滤规则显式化、可审计；网关不落业务数据 |
| ③ | **中心单点**（通讯+账本压在一处） | 账本 append-only + 定期快照；跨机走中继不共享库；备好故障恢复手册 |
| ④ | **留痕可篡改**：当前 append-only 但没有哈希链/签名 | 按下方"最小可信留痕清单"补齐 |
| ⑤ | **责任链**：组织不变 = 责任仍在人，干活可外包、担责不能外包 | 每个节点记"谁的办公室经手"；批准动作必须绑定到**人**并留实名 |
| ⑥ | **数据边界与隐私**：向上接入时上一层能看到多少 | 网关默认**最小上报**：只上报案卷状态与节点摘要，不上报私人信件正文——"信是正文，案卷是索引"，上行只走索引 |
| ⑦ | **合规/审计**：企业第一问是鉴权、审计、零信任 | 阶段三前补齐统一鉴权、审计导出、沙箱隔离；把 localhost-only、无鉴权的现状**显式声明**为边界 |

**最小可信留痕清单（建议）**：
1. 案卷 **append-only**（已具备），追加即写、不可改不可删；
2. 节点记录 `时间 + 经办（身份/办公室）+ 动作 → 状态`，**[自动] 节点与人工批示可区分**（已具备）；
3. 每节点计算**前序哈希**，形成**哈希链**，首节点锚定案子 ID；
4. 关键收局（中止/办结）与复核双签**附加签名**；
5. 提供**校验命令**：任取一节点即可验证其前链路完整、未被篡改；
6. 封卷后**只读**（已具备），重开走新案卷并引用旧卷；
7. 审计导出为**自包含、可离线校验**的片段，不只依赖本地库在线。

这七条让"工单 + 审计 + 信誉"从口号变成可举证的凭证。

## 十二、结论与建议

**三条战略建议**：

1. **别自造协议，兼容 A2A。** 异质 agent 互通的标准化已被 A2A 占位（Agent Card ≈ 配置条目，task ≈ 案卷）。要做的是**对齐**，不是另立山头——自造协议只会增加集成成本而换不来差异化。
2. **切位切在 A2A 的留白处。** A2A 解决了"agent 怎么互通"，却对**编排 + 案卷/信誉 + 部门治理**故意留白。差异化不在传输层，而在于把**案卷（工单 + 审计 + 信誉三合一）**做成那一层，并叠上"逐层接入 + 组织不变"的落地路径。别人把 agent 收进自己的运行时，我们让 agent 留在自己的 harness，只共享契约。
3. **先把单机闭环做实。** 个人层是种子层，也是当前唯一在排期的东西。所谓"先做强、不先做大"——不碰部门与企业排期，把窗口/案卷/应用打磨到可交付、可验证、测试全绿，再谈向上接一层。

**一句话收尾**：个人信息中心是整张蓝图的种子——它既是**最小可运行的完整样本**（通讯 + 账本 + 案件 + 信誉雏形一应俱全），也是**同一套软件递归装三次的第一层**；这一层的架构选择（薄中心、案卷、去中心认领、责任留痕）会被原样复制到部门与企业，因此它做对了，整张蓝图才立得住。
